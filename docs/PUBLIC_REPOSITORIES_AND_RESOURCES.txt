SOLVER AI - PUBLIC REPOSITORIES AND STUDY RESOURCES
Project: https://github.com/arunabanarjee32-bit/solver-ai
Updated: 2026-11-15

PURPOSE
Consolidated inventory of repositories and resources previously discussed
for the Solver AI / AlgoMind AI vision: a LeetCode/Codeforces/ICPC
practice platform with secure judging, explainable AI solving, adaptive
tutoring, and optional self-hosted fine-tuned models.

IMPORTANT
- This is a STUDY / CANDIDATE list, not a list of installed dependencies.
- Do not merge or fork all repositories wholesale into Solver AI.
- Review exact versions, copyright, upstream licenses, security, activity,
  maintenance and operational requirements before reusing anything.
- Public source code does not imply unrestricted commercial rights.
- Dataset and problem-statement rights are separate from repository licenses.
- Favor one modular Solver AI monorepo; use adapters/dependencies/services.
- The current Solver AI repository has working local web, auth, API,
  and gVisor judge foundations according to docs/PROJECT_STATUS.md.
- In particular Monaco, Better Auth and FastAPI have been integrated.
  Keep existing tested functionality unless a technical audit justifies change.
- The status of each OTHER candidate is not asserted here.

==============================================================================
RECOMMENDED STUDY ORDER TO AVOID UNNECESSARY CODEX SPEND
==============================================================================
1. Read docs/PROJECT_STATUS.md and existing tests before adding dependencies.
2. Keep existing Next.js/Monaco, Better Auth, FastAPI and gVisor work.
3. Review phi-code and CodeSIM as AI research references, not copy-paste APIs.
4. Use judge references (Piston/QingdaoU/DMOJ/MOJ) only for specific gaps,
   after threat model, license review and proof that current judge needs change.
5. Add a model-provider interface and verifiable tutor workflow before training.
6. Benchmark untuned models before choosing Hugging Face/Unsloth/vLLM stack.
7. Defer enterprise search, large contest engines and expensive GPU work
   until validated feature requirements demand them.

HOW TO CONTRIBUTE A NEW REFERENCE
- Provide exact repository URL and the problem it solves.
- Note whether it is a dependency, service, reference or rejected option.
- Review license, health, security, integration cost and current alternatives.
- Record an ADR for a major architecture choice, and test actual integration.
- Update this file plus docs/OPEN_SOURCE_STRATEGY.md when adopted or rejected.
