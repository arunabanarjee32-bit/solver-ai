3. CONFIRMED ISSUE REQUIRING REMEDIATION

JUDGE-001 — Failed Docker cleanup can lose controller tracking.
Classification: confirmed operational recoverability weakness; medium impact.
Evidence at baseline: services/judge/solver_judge/control/runner.py:93-98 and 163-166.
_remove suppressed RuntimeError/OSError, while the context manager discarded the
container name regardless of removal outcome. A daemon/removal failure could
therefore leave an orphan sandbox indistinguishable from an absent container.
There is no evidence of exploitation or host escape from this finding.

Remediation: RESOLVED in source commit1336354, with12 new cleanup/readiness
regressions. The final judge suite passed118 cases including15 live gVisor tests;
the full browser suite passed25 cases including real submissions and ownership.
Failed cleanup retains names, confirms absence through bounded queries, revokes
runner readiness and stops worker heartbeat renewal/new claims. Current-lease
completion still reports a safe verdict. API capability display retains its existing
60-second expiry window; no unready runner is allowed to execute new work.
Process-crash reconciliation and production monitoring remain separate gates.

4. CONFIRMED LIMITATIONS, NOT OBSERVED LOCAL BYPASSES

API identity transport:
services/api/solver_api/features/identity/verification.py:163-175 accepts configured HTTP or HTTPS JWKS
URLs. Callers cannot select this URL through token headers. Internal Compose
uses HTTP intentionally. External production JWKS traffic requires HTTPS or an
explicitly trusted internal route; an untrusted cleartext path would allow key
substitution. This is a deployment trust requirement, not a demonstrated local
signature bypass. HTTPX timeouts and a 64 KiB cap exist, but the full streamed fetch
has no outer total deadline; slow configured issuers can impair availability.

Data lifecycle and capacity:
services/api/solver_api/features/submissions/store.py stores owned source/history durably.
Ownership and 0600 file permissions do not provide a retention/deletion policy,
encryption-at-rest operation, cumulative storage cap or tested backup/restore.
Submission-specific rate, active-work and queue limits exist. Aggregate API
concurrency/ingress quotas and future model cost budgets remain production work.

Worker trust:
API control requires a nonempty shared token compared in constant time and uses
separate leased completion tokens. The API does not itself enforce minimum shared
token entropy or per-worker identities. Native launcher generation is stronger.
Production controller networking, rotation and worker trust need an explicit
operation policy; no missing-auth bypass was identified.

Web identity and privacy:
Local email/password accounts lack delivered verification/recovery email.
Already issued offline-verifiable API JWTs last up to five minutes after session
logout. Local forwarding headers are disabled to resist spoofing, leaving shared
throttle buckets; production needs trusted ingress configuration. Browser drafts
are localStorage state, best effort and not account-encrypted backups. They are
not uploaded continuously by the existing editor workflow.

Judge infrastructure:
The rootless prototype uses per-process limits and bounded temporary storage,
not aggregate cgroup resource accounting or complete host-wide budgets. The
recorded gVisor runtime is older than the upstream release previously reviewed.
Independent runtime/security review and maintained production operations remain
release gates. MLE is accepted in protocol vocabulary, but ambiguous allocation
failure is conservatively RE; do not claim precise measured MLE was demonstrated.
No finite test suite can certify the absence of sandbox escape.
