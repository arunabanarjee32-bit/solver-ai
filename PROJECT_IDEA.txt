SOLVER AI
A detailed project idea for learning, testing and improving algorithmic reasoning

Prepared: 17 November 2026 (Asia/Kolkata)
Document type: product vision and staged delivery proposal

Read this first
This document describes one complete project that can grow from the software
already present. It separates existing capabilities, proposed work and research
ambitions. A feature described here is not implemented merely because it appears
in this file. The current implementation record remains docs/PROJECT_STATUS.md;
technical decisions and development instructions remain in docs/.

The owner has reported unwanted repository changes. That report motivates careful
preservation and review, but this document does not establish who made a change
or prove that an account or repository was compromised. Files placed under
AnalyseFuture are preserved material for assessment, not an accusation and not
an endorsement of their contents.


1. THE CENTRAL IDEA

Solver AI should become an independently controlled workspace where a person can
learn an algorithm, attempt a problem, test a program, understand a failure and
improve their reasoning. An optional AI assistant should help throughout that
process while showing the limits of its evidence.

The essential experience is a continuous learning loop:

    Understand -> plan -> implement -> test -> explain -> reflect -> revisit

Most learners can already ask a chatbot for code. The harder product problem is
helping them decide whether the code is relevant, why it works, what it fails on,
what they have understood and what they should practice next. Solver AI should
join those steps through a real judge, thoughtful teaching and a record of the
learner's work.

The promise should be: "Build algorithmic skill with explanations and observed
evidence you can inspect." It should not be "Every generated answer is correct"
or "AI will win every contest for you."

There are two related experiences inside the same project. Learning mode helps a
person develop skill with limited spoilers. Research mode investigates how well
a model or solving strategy performs under a fixed budget. They share problem
definitions and safe execution, but their goals and assistance rules differ.


2. WHAT ALREADY EXISTS AND MUST BE PRESERVED

The repository already contains a meaningful local practice foundation:

* A Next.js and TypeScript web application with an original problem catalog,
  problem pages, a locally bundled Monaco editor and browser drafts.
* Python and C++17 editing and an optional gVisor-isolated execution workflow.
* Better Auth accounts, session controls and user-owned submission history.
* A Python FastAPI catalog, authenticated requests and a durable SQLite queue
  with ownership checks, worker leases and bounded completion summaries.
* A separate judge control worker, sandbox probes and tests of verdicts and
  hostile program behavior.
* Author-written hints and an authenticated offline hint API contract.
* Dependency locks, local startup commands, builds, tests and CI configuration.

These are existing components, not a reason to restart the project from zero.
Their exact working state must be checked after changes. Historical test results
do not automatically validate a new revision or a production deployment.

Important gaps remain. The hint backend is authored content, not model inference.
The new hint API is not yet the browser's model-backed tutor. There is no complete
AI solver, contest system, production identity operation or public production
deployment. Local accounts lack delivered verification and recovery email.
SQLite persistence and a local sandbox prototype are not production operations
or an independent security certification.


3. WHO THE PROJECT SERVES

The first audience should be DSA learners and early competitive programmers.
They need clear statements, reliable feedback and a path from basic reasoning
to independent solutions. Narrowing this first audience keeps delivery realistic.

Later audiences can include:

* Interview candidates who want topic practice and explanation of tradeoffs.
* Experienced competitors studying advanced algorithms and unusual failures.
* ICPC teams reviewing strategy, communication and post-contest mistakes.
* Coaches and educators creating permissioned practice sets and reviewing work.
* Problem authors checking statements, constraints, validators and references.
* Researchers comparing models and solving strategies reproducibly.
* Institutions conducting assessments under an explicit assistance policy.

These audiences should not all receive a different application. They should use
the same core project with role permissions, appropriate screens and clear modes.
Institutional assessments and rated events need stronger identity and integrity
controls than ordinary self-directed practice.


4. THE EXPERIENCE WE SHOULD BUILD FIRST

A learner opens an original or permissioned problem, understands its constraints
and writes a Python or C++17 solution. The editor saves a draft without uploading
every keystroke. The learner runs public samples, submits deliberately and sees a
real verdict rather than a simulated success message.

When stuck, the learner can choose a small hint. The first hint identifies a
useful concept; the next offers an observation; a later hint suggests a plan.
Full code should be an explicit choice, not the default response. Each hint must
say whether it is author-written or model-generated.

After a failed submission, the interface explains what is actually known. A
compilation error can show a capped compiler message. A timeout can explain the
resource limit. A wrong answer should not invent a root cause that the evidence
does not establish. Private grading inputs and expected answers stay private.

After success, the learner compares approaches, discusses an invariant and
records a short reflection: "What did I miss? What makes this approach work?"
Later, a related problem checks whether the understanding transfers. The product
should reward independent improvement, not only the number of accepted answers.


5. FOUR CLEAR MODES

PRACTICE AND TUTOR
Progressive hints, small questions, conceptual explanations, examples and
reflection. The learner controls spoiler level. Assistance should reduce when
the learner can proceed independently.

DEBUG
The user deliberately provides code and relevant public evidence. The assistant
tries to reproduce the issue through the isolated judge, distinguishes observed
failure from hypothesis and proposes the smallest useful correction. It should
explain the correction and invite the learner to test it.

SOLVER AND RESEARCH
An authorized user requests a complete attempt. The system proposes a plan,
generates bounded candidates, runs permitted tests and returns an explanation,
complexity estimate, evidence and remaining uncertainty. It records the model,
strategy and budget so results can be compared fairly.

CONTEST
The event declares what assistance is allowed. Server-side permissions enforce
the policy; hiding an AI button is insufficient. Restricted live events disable
forbidden assistance. Post-contest review can enable it when the policy allows.


6. ONE PROJECT, WITH PURPOSEFUL LANGUAGE CHOICES

Keep one modular repository and one product identity. One project does not mean
every component must use the same programming language or share one process.

TypeScript and Next.js suit the browser interface, editor, accessibility and
interactive account flows. Python and FastAPI suit existing application services
and future model orchestration. The judge remains a separate execution boundary.
The browser communicates through documented, validated API contracts.

Conceptual structure:

    Web application and editor
                |
    Authenticated API and policy checks
          /                   \
    Submission queue       Tutor / solver orchestration
          |                   |
    Isolated judge       Approved model provider adapter
          \                   /
        Bounded evidence, history and explanations

Initially add AI modules inside the existing backend where sensible. Create a
separate AI service only when resource isolation, deployment or measured load
justifies it. Avoid adding services merely to make the architecture look larger.

Learner languages are a separate decision from implementation languages. Adding
Java, JavaScript, Rust, Go or C++20 later requires an audited runtime, compilation
contract, limits, tests, diagnostics and maintenance. A dropdown alone does not
mean a language is supported.

A single-language rewrite is technically possible for parts of the application,
but it would replace working components and port AI integrations. There is no
current evidence that such a rewrite improves the core learner experience.


7. HOW THE TWO ARCHIVES CAN CONTRIBUTE

CodeGenerator and phi-code are valuable research references for the future AI
workflow. The originals and extracted material belong under AnalyseFuture for
preservation and assessment. Unpacking them does not integrate or validate them.

CodeGenerator suggests a useful sequence: propose an algorithmic plan, challenge
the plan, generate code and allow a limited debugging loop. phi-code suggests
generating diverse attempts and ranking candidates using test evidence.

We should adapt ideas through original, reviewed interfaces rather than replace
the application with both upstream frameworks. Preserve relevant licenses and
notices if any code is later reused. Code licensing, problem-content rights,
dataset permissions and model-weight licenses require separate review.

Do not adopt archive code that runs generated programs through host Python,
unrestricted subprocesses or exec inside the application. Do not treat benchmark
datasets, contest anecdotes or similarity scores as proof of general ability.
Archive data remains reference material until its permitted uses are established.


8. A REALISTIC AI SOLVING PIPELINE

The future pipeline should operate only on authorized, versioned problem data:

1. Validate the statement, constraints, input/output contract and requested mode.
2. Check account permissions, event policy and remaining usage budget.
3. Construct bounded context from public material and consented user input.
4. Request a concise algorithm plan and assumptions from the chosen provider.
5. Generate a small, explicitly limited number of candidates.
6. Compile and run candidates through the existing isolated execution pathway.
7. Use samples and approved additional tests to compare observed behavior.
8. Repair only when the budget permits and evidence supports another attempt.
9. Return the selected attempt with an explanation and explicit evidence limits.

Every run needs limits on input size, tokens, candidates, test jobs, elapsed time,
concurrency and spend. Stop on cancellation, exhausted budget, unsafe inputs,
provider failure or sufficiently useful completion. An endless retry loop is not
an acceptable product feature.

Differential testing is useful only with a trustworthy oracle. Metamorphic tests
are useful only when their claimed relationship is valid. Random case generation
can miss important cases. A model-created test and a model-created solution may
share the same mistake. Use independent checks where possible.

Rank candidates primarily by authorized execution evidence and clear policy.
Sentence similarity and model confidence may be research signals, but they are
not functional correctness. Report "passed this finite set of checks," not
"mathematically verified," unless an actual proof system supports that claim.


9. PROVIDERS, DATA AND MODEL RESEARCH

Begin with one real provider behind a neutral interface, with authored hints as a
clearly labeled fallback. Support timeout, malformed output, refusal and outage
without breaking ordinary practice. Users should know when their submitted code
or question will be sent to a third party.

Provider URLs and credentials belong in trusted configuration, not user-provided
request fields. Responses are untrusted content and need schema validation and
safe rendering. Problem text, uploaded files and model output must not override
system permissions or request arbitrary network access.

For each problem or dataset, record provenance, author, version, permissions and
allowed uses. Training, redistribution and commercial use are different rights.
Do not scrape private tests, bypass access controls or assume that a public page
grants unrestricted reuse. Private submissions require explicit training consent.

Fine-tuning should be a later experiment, after a strong baseline exists. Start
with a small, rights-approved dataset, deduplication and clean evaluation splits.
Use external approved compute with a fixed budget. Compare the result against
the original model; keep it only if measured quality or economics improve.
Collecting a large dataset or downloading weights is not itself an improvement.


10. THE JUDGE AND PRODUCTION SAFETY

Generated code and learner code are equally untrusted. Keep execution away from
API credentials, account data, provider secrets and private grading answers.
Missing isolation must fail closed. There must be no automatic fallback to host
execution or ordinary application containers.

Before a public launch, the judge needs maintained runtime infrastructure,
host-wide resource budgets, independent review and an operational incident plan.
Existing per-process limits are not the same as aggregate resource accounting.
Do not infer exact peak memory from an error string or claim that passing a test
suite proves a sandbox cannot be escaped.

Production identity needs verified deployment configuration, recovery policies,
trusted ingress rules and abuse controls. Production data needs tested backups,
restore drills, retention and deletion processes, access review and redacted logs.
Separate development accounts and benchmark state from real learner records.

The reported repository disruption also makes provenance useful: retain a record
of moved files and archive checksums, avoid destructive history rewriting and
review unexpected changes. File organization alone does not establish that an
account is secure or replace an account access review by its owner.


11. LEARNING FEATURES THAT CAN MATTER IN THE AI ERA

As code generation becomes common, reasoning, verification and judgment become
more valuable. Useful directions include:

* Explain an invariant before revealing code, then test understanding on a new
  example rather than asking the learner to repeat the explanation.
* Compare two plausible algorithms and identify the constraint that chooses one.
* Create a small permitted counterexample that exposes a specific misconception.
* Review AI-generated code and distinguish elegant wording from valid reasoning.
* Practice debugging a correct-looking program with a subtle boundary failure.
* Revisit a topic after a delay to measure retention and transfer.
* Keep a learner-controlled notebook of mistakes, proofs and improvements.
* Offer post-contest team reviews about decisions and time allocation.
* Let educators inspect evidence and assistance levels instead of only scores.

These are proposed product directions. Personalization should be explainable and
editable; a few failed attempts cannot diagnose a person's ability. Avoid labels
that discourage learners or imply psychological certainty.

Accessibility should be part of the first usable workflow: keyboard controls,
clear focus, readable contrast, screen-reader labels, capped structured error
messages and layouts that work on narrow screens. Localization and low-bandwidth
support are valuable later, but require testing with the intended users.


12. DELIVERY PLAN: NOW AND THE NEXT 12 MONTHS

These are planning horizons, not guaranteed dates. Advance when evidence and
resources justify the next step. A small team may complete fewer milestones.

NOW: RESTORE CLARITY AND KEEP THE FOUNDATION WORKING
Preserve existing work, inventory every archive and document the active paths.
Keep uncertain reference material in AnalyseFuture. Validate the existing web,
API, auth and isolated submission workflow. Establish a known revision and a
clear account of what passed, failed or was not run.

NEXT: A SMALL REAL TUTOR PILOT
Choose a first learner group, agree content rights and ownership decisions, then
connect one bounded model provider to the existing hint contract. Add a modest
set of original problems and a typed, accessible hint interface. Measure whether
learners find it useful before expanding the catalog or adding more providers.

WITHIN A POSSIBLE FIRST YEAR
Improve production identity and judge operations, pilot consented debugging,
build a small evaluation harness and test a bounded candidate-solving workflow.
Add useful learning paths and basic authoring only when ownership and quality
can be maintained. Do not make paid training, rated contests or many language
runtimes prerequisites for this first useful product.

Exit evidence: a fresh developer can start the documented workflow; authorized
users can submit correct and incorrect programs; ownership and isolation tests
pass; model quotas and outage behavior are exercised; a small pilot yields
documented user feedback. A public release requires its separate operational gate.


13. DELIVERY PLAN: 12-24 MONTHS AND BEYOND

POSSIBLE SECOND YEAR
If the pilot shows sustained value and funding supports operations, expand the
original problem library, improve feedback quality and add coach dashboards.
Evaluate virtual contests and ICPC practice with tested scoring, freezes, event
permissions and post-contest review. Add languages one at a time with full runtime
coverage. Explore self-hosted inference only if quality, staffing and economics
justify its ongoing cost.

POSSIBLE THIRD YEAR AND LATER
Consider carefully evaluated fine-tuning, stronger research tooling, institutional
deployments, richer collaboration and selective formal verification. A proof
assistant may verify restricted exercises with explicit specifications; that is
different from proving arbitrary generated competitive-programming solutions.

Longer-term opportunities include multilingual teaching, offline educational
packages, accessible visualization, organization-controlled providers and open
evaluation reports. Each should enter the roadmap through a user need, an owner,
an acceptance gate and a budget. "AI may improve in two years" is not a substitute
for a present implementation strategy.


14. WHO WILL BUILD, TRY AND MAINTAIN THESE FEATURES

The project owner sets priorities, approves spending and settles licensing,
privacy, hosting and assistance policies. An AI coding assistant can help inspect,
implement and test approved work; it does not become the legal owner, security
operator or permanent maintainer by producing code.

Initially one developer may cover several roles. As usage grows, the needed
responsibilities are:

* Product and teaching: learner interviews, curriculum, hint quality and outcomes.
* Frontend: accessible editor, account flows, history and clear evidence displays.
* Backend: contracts, authorization, queues, quotas and reliable persistence.
* Judge and infrastructure: isolation, runtime updates, capacity and incidents.
* AI and evaluation: provider integration, reproducibility, budgets and regressions.
* Content and rights: original problems, test quality, permissions and corrections.
* Community and operations: support, moderation, privacy requests and abuse handling.

Early learners and coaches should try features in small pilots. Researchers can
evaluate solver methods on held-out data. Institutions can test assessment modes
after integrity and identity controls exist. No named organization or future
contributor is assumed to have committed to this work.


15. MEASURE SUCCESS WITHOUT INVENTING ACHIEVEMENTS

Establish a baseline before setting numerical release targets. Record the exact
revision, environment, model version, problem set, budgets and evaluation method.

Measure learner return rate, useful practice completed, hint helpfulness and
performance on later independent problems. Consider assisted and unassisted
attempts separately. Time spent and accepted submissions alone do not prove
learning, and an observational pilot does not establish causation.

Measure judge correctness on maintained fixtures, queue latency, job failure and
cancellation behavior, isolation regressions and recovery success. Distinguish
application failures from user-program verdicts.

For research, report pass@1 and pass@k under a stated sampling protocol, cost,
latency and failures. Use disjoint, rights-approved evaluation data and explain
possible contamination. Compare a single-candidate baseline with repair and
ranking variants using comparable budgets. Publish negative results when useful.

Before promotion, require a relevant regression suite, documented limitations,
owner review and a rollback path. A written plan, imported archive or zero-test
run cannot satisfy a feature acceptance gate.


16. COST AND A SUSTAINABLE BUSINESS

The initial product can remain useful without external AI calls through its
catalog, judge, authored hints and history. Keep that path available. Start model
usage with small quotas and explicit per-run ceilings, not unlimited generation.

Track provider tokens, execution time, storage, egress, support and infrastructure
cost per useful workflow. Warn users before an optional action consumes a paid
allowance. Stop when a hard limit is reached; do not silently switch to more
expensive models or repeat failed calls indefinitely.

Possible later revenue sources include individual premium tutoring allowances,
coach tools and institutional hosting or assessment subscriptions. Validate
willingness to pay and operational cost before implementing billing. Paid users
must not bypass contest integrity or receive misleading correctness promises.

Self-hosting trades provider fees for hardware, utilization, maintenance and
security obligations. Fine-tuning adds data and evaluation costs. Neither should
be presented as automatically cheaper or necessary for independence.


17. WHAT WE CANNOT HONESTLY PROMISE

* Guaranteed correctness or termination for arbitrary programs and specifications.
  General automated guarantees have fundamental limits; restricted proofs remain
  possible when assumptions and specifications are explicit.
* Solving every ICPC problem, replacing every coach or delivering universal
  personalized teaching. Performance depends on tasks, evidence and resources.
* Proving correctness from samples, random tests, similarity or model confidence.
* A perfectly secure sandbox, flawless account system or zero cheating. These need
  ongoing defense, independent review and incident response.
* Reconstructing deleted or unknown historical work without recoverable evidence,
  or attributing reported unwanted changes without a proper investigation.
* Replicating a mature commercial platform with a small initial team and budget.
* Treating public problems, archives, user code or model weights as unrestricted
  training and commercial material.
* Training a competitive foundation model in this development workspace, or
  assuming future GPU access, funding or outside contributors will materialize.
* Claiming hosted deployment, benchmark gains, production readiness or educational
  improvement merely because code or a roadmap has been committed.

Uncertainty should become an explicit research question or delivery dependency,
not disappear from the product description.


18. THE FIRST COMPLETE PRODUCT WE SHOULD AIM TO DELIVER

The first complete product is deliberately focused: an original problem opens,
the learner writes code, an isolated judge returns a trustworthy finite verdict,
the learner gets an optional clearly labeled hint, and their private history
helps them improve on the next attempt. A small real provider pilot can extend
that workflow once privacy, entitlement, cost and quality controls are ready.

Preserve the work that already supports this experience. Treat AnalyseFuture as
an organized reference area and bring selected material into the active project
only through an explicit review. Keep the product idea ambitious while making
each delivered capability concrete, observable and maintainable.

The long-term opportunity is a place where people learn to reason well with AI,
test what AI proposes and remain responsible for the conclusions. That is a
stronger foundation for the coming years than promising an automatic answer to
every programming problem.
